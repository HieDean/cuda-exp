# 一些感性的分析

## gemm_v0
最简单的版本。一个线程计算 C 中的一个数。

## gemm_v1
由于 v0 版本对于 A 和 B 都有多次重复访问，为了缓解重复访问效率低的问题，采用分块计算，每次把一小块数据放到共享内存中，然后重复访问共享内存，这要比重复访问全局内存高效很多，仍然是一个线程计算 C 中的一个数。

## gemm_v2
一个线程只计算 C 中的一个数太低效了，为了提高计算访存比，我们希望一个线程能计算 C 中的多个数。v2 的版本中，我们实现了一个线程可以计算 C 中的 4 个数。

## gemm_v3
一个线程只能计算 C 中的 4 个数太死板了，v3 实现了可以通过调整 tile 大小和 block 大小来实现一个线程计算 C 中的若干个数。并且从平衡 block 个数和提升计算访存比的角度上，前人有一些实验给出了较优的 tile 大小和 block 大小设置，v3中直接延用了。

同时 v3 采用了寄存器数组的方式来保存外积计算过程中需要的重复访问的数据，进一步提高计算访存比；

## gemm_v4
v4 主要是实现了 warp 重组，其目的也是优化计算访存比。

## gemm_v5
v5 使用 FLOAT4 对共享内存进行向量化访存，之所以不对全局内存也进行向量化访存是因为使用 FLOAT4 需要内存对齐，共享内存是我们自己定义的天然内存对齐，但全局内存和用户输入有关，为了 kernel 的通用性所以不能要求其对齐。

同时使用向量化访存要对 A 矩阵的 tile 进行转置，这会导致写入 A 的共享内存时出现 bank conflict，因此需要使用 swizzle。

另外，为了尽可能减少访问共享内存时的内存事务，v5 使用了 z-order，详细原理还需要再参考 ref1 和 ref2 悟一悟。

最后还发现，如果 for 循环中使用过多的循环条件，会影响编译器优化，性能会变拉。

## gemm_v6
写好 v5 之后，我将 v5 和 ref1 中的代码做了性能对比，发现 v5 很拉，但明明该有的优化措施都完成了，百思不得其解，于是逐行对比修改，最终发现当给 float 类型的共享内存数组元素赋值 0.0 的时候，性能会下降，如果直接赋值 0.0f，性能就会变好。

可以看到 v6 几乎和 ref1 中的逻辑没有区别了。

## gemm_v7
主要实现了双缓冲队列，但是发现在 3090 上编译运行的话，性能没有问题，在 5060ti 上编译运行的话，性能反而不如 v6，通过在编译时添加标志位`target_compile_options(gemm_test PRIVATE $<$<COMPILE_LANGUAGE:CUDA>:-Xptxas> $<$<COMPILE_LANGUAGE:CUDA>:-v>)`发现在 sm_120 架构下 v7 kernel 用了 139 个寄存器，但在 sm_86 架构下只用 127 个寄存器，ncu 也告诉我 v7 kernel 性能拉是因为寄存器溢出，于是搞了一堆措施企图限制编译时，给 v7 kernel 的寄存器个数，不过目前也只能是在 5060ti 上稍微好一点，仍然没有超过 v6 和 ref1 的实现。
